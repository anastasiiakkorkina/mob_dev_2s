# Demo 4–5 — ошибки, исправления и ответы

До исправлений: коммит `17540b38b82f01e2584bdcfcd93d89dfb52567f5`.
Проверка выполнена в отдельном профиле Chrome с DevTools, открытыми на Console до действий. Личные данные основного браузера не менялись. Проверочные скрипты были временными, в проект не добавлены.

## Demo 4 — интерфейс работает, но Console показывает ошибку

**Как повторить до исправления:** открыть приложение через HTTP → открыть DevTools / Console → нажать Evidence, затем Dashboard. Страницы переключаются, но при каждом нажатии появляется:

```text
TypeError: Cannot read properties of undefined (reading 'getAttribute')
    at HTMLButtonElement.<anonymous> (.../modules/event_listener.js:15:38)
```

**Причина:** обработчики создавались в цикле с `var i`. Когда пользователь нажимал кнопку, цикл уже закончился, `i` был равен 5, а `navButtons[5]` не существовал. Сам переход всё равно работал через отдельный `onclick` в HTML.

**Исправление:** обработчик теперь берёт кнопку через `event.currentTarget`, а не через старый индекс цикла:

```js
navButtons[i].addEventListener("click", function (event) {
  var targetView = event.currentTarget.getAttribute("data-view");
  console.log("nav clicked:", targetView);
});
```

**Проверка:** все пять кнопок нажаты многократно. Переходы работают, ошибки больше нет; остаются нормальные сообщения, например `nav clicked: evidence`.

**Ответ на вопрос:** ошибка обнаружилась по красному сообщению в Console, хотя страницы открывались. Видимый результат выполнял один обработчик, а другой падал. Поэтому «на экране всё нормально» ещё не означает, что весь код работает правильно.

## Demo 5 — остальные найденные ошибки

В каждом пункте: как повторить → что было вместо ожидаемого → причина и исправление → проверка.

### 1. Dashboard не обновлял счётчики

Открыть Dashboard → в Evidence добавить закладку и поменять E02 на Reviewed → вернуться. Оставались `Bookmarked: 0`, `Reviewed: 1`, хотя в данных уже `1` и `2`.
Причина — Dashboard рисовался только один раз. Теперь он перерисовывается при каждом переходе. Проверено сравнение счётчиков с текущими данными после изменений.

### 2. Recent evidence показывал не самые новые улики

Сравнить Recent evidence на Dashboard с Evidence → Newest first. Наборы не совпадали: Dashboard показывал `E18, E17, E16, E15, E14`.
Причина — последние элементы JSON ошибочно считались последними по времени. Теперь копия массива сортируется по `timestamp`, и берутся первые пять: `E14, E03, E04, E13, E01`. Проверено совпадение с сортировкой по дате и сохранение исходного массива.

### 3. Смена статуса стирала несохранённую заметку

Открыть E02 → написать заметку без Save note → поменять Review status или Relevance. Текст исчезал, хотя пользователь менял другое поле.
Причина — вся карточка создавалась заново со старой сохранённой заметкой. Убрана лишняя перерисовка карточки; список улик обновляется по-прежнему. Проверено: текст остаётся при обеих сменах и затем сохраняется кнопкой.

### 4. Текст заметки воспринимался как HTML

Сохранить `<b>my note</b>` → посмотреть Note preview и Workspace. Вместо букв с тегами показывался жирный текст.
Причина — пользовательский текст вставлялся в `innerHTML`. Теперь используется `textContent`, а для textarea — `value`. Проверены теги, `&`, строка `</textarea>`, повторное открытие и перезагрузка: это обычный текст, новые HTML-элементы не создаются.

### 5. Ссылка от человека сохраняла чужие фильтры

В Evidence ввести `zzzzzz` → People → нажать `view` у человека. Ожидались его улики, но список оставался пустым.
Причина — менялся только фильтр человека, старый поиск продолжал действовать. Теперь перед переходом остальные фильтры очищаются. Проверены ссылки всех шести людей дважды: количество карточек соответствует их связям.

### 6. Timeline показывал `[object Object]`

Открыть Timeline → посмотреть строку Location. Вместо названия места выводилось `[object Object]`.
Причина — в текст добавлялся целый объект места. Теперь берётся `evtLoc.name`. Проверены оба порядка событий и фильтры: названия отображаются нормально.

### 7. Окно Timeline накапливало обработчики

Три раза открыть `View …` и закрыть окно. Console показывала `modal opened, active close listeners: 1`, затем `2`, затем `3`.
Причина — к одному окну при каждом открытии добавлялась новая функция обработки клика. Проверка `getEventListeners(document.getElementById('quickViewModal')).click.length` в DevTools подтвердила три настоящих обработчика.
Теперь обработчик подключается один раз при создании окна. После повторных открытий их количество равно 1; закрытие и Open full evidence работают.

### 8. Повреждённый localStorage ломал приложение

В отдельном тестовом профиле через Application → Local Storage записать `{` в `remotion_notes` и перезагрузить. Приложение зависало на загрузке из-за `JSON.parse`. Значение `null` в `remotion_hypothesis` ломало открытие Workspace.
Причина — сохранённые данные читались без достаточной проверки. Теперь ошибки разбора перехватываются и проверяется тип значения. Испорченные данные заменяются безопасными значениями в памяти; всё хранилище не очищается.
Проверены `{`, `null`, `[]`, `42`, неверные типы отдельных полей. Приложение открывается; при некорректном JSON остаётся понятное предупреждение, а не необработанная ошибка.

### 9. Неверные закладки и нулевая уверенность

Записать в `remotion_bookmarks` значение `["E01","E01","missing",123]`: Dashboard считал четыре закладки, хотя существует только одна подходящая улика. Теперь удаляются повторы, неверные типы и неизвестные ID.
Записать в `remotion_hypothesis` `{"confidence":0,"evidenceIds":[]}`: Workspace показывал 50 вместо 0. Причина — `0 || 50` возвращает 50. Теперь число проверяется отдельно и ограничивается диапазоном 0–100. Оба примера проверены после перезагрузки.

### 10. Гипотеза не сохранялась автоматически

Workspace → заполнить поля без нажатия Save → перезагрузить. Текст терялся, хотя инструкция на Dashboard обещает автоматическое сохранение.
Причина — сохранение было подключено только к кнопке. Теперь изменения полей также вызывают сохранение. Проверены текст, выбор человека и улик, характер события, пустое поле, уверенность 0, уход на другой экран и перезагрузка. Кнопка Save также работает.

### 11. Раздел открывался раньше завершения загрузки

Сохранить закладку E01 → открыть сразу `/#workspace` → замедлить ответ `evidence.json` → перезагрузить. Общий экран загрузки исчезал раньше ответа; Workspace показывал отсутствие закладок и не обновлялся после получения улик.
Причина — `loadEvidenceData()` не возвращал Promise, а `loadAllData()` не ожидал загрузки улик и Timeline. Теперь операции связаны возвращаемыми Promise; начальная навигация и снятие общего индикатора происходят после завершения цепочки. Здесь используется последовательная загрузка, без перехода на async/await.
Проверены задержанный ответ, смена адреса во время ожидания, перезагрузка в этот момент и старт с `/#workspace`: сохранённая закладка появляется.

### 12. Ошибки загрузки выдавались за пустые данные

При ответе HTTP 500 с телом `[]` для `people.json` приложение показывало ноль людей, а для `timeline.json` — отсутствие событий. Ожидалось сообщение о сбое.
Причина — `fetch()` не отклоняет Promise только из-за HTTP 500; код не проверял `response.ok`. Добавлены проверки для case, people, locations и timeline. Ошибка основных данных останавливает индикатор и сообщает о проблеме; ошибка Timeline отображается в самом разделе. Проверен HTTP 500 для всех пяти JSON-файлов, включая уже исправленный в Demo 3 evidence.

### 13. В Console выводился Promise вместо заметки

При открытии приложения было `First note preview: Promise`, даже если заметка уже сохранена.
Причина — логировался результат вызова `loadNoteAsync()`, то есть Promise. Теперь вывод находится внутри `.then()` и получает текст заметки. При пустой заметке лог содержит пустую строку, а не Promise.

## Что проверено целиком

Дважды пройдены Dashboard, четыре сортировки Evidence, все пять фильтров, поиск, закладки, подробности, статус, relevance, сохранение и очистка заметок; вкладки People/Locations, все ссылки людей; сортировки и три фильтра Timeline, открытие/закрытие окна и полный просмотр; Workspace и поля гипотезы с перезагрузкой.

Дополнительно проверены быстрый ввод и очистка поиска, уход во время поиска, повторный выбор фильтра, повторные переходы, пустые значения, изменённый localStorage, задержанные и ошибочные ответы. На ширинах 1280, 768 и 390 пикселей горизонтального переполнения страницы не обнаружено.
В обычном проходе необработанных ошибок JavaScript нет. При специально повреждённых данных или сбое сети диагностические предупреждения/ошибки ожидаемы. Статус и relevance остаются изменениями текущей сессии: их сохранение после перезагрузки в этом задании не добавлялось.

## Короткий сценарий для показа на занятии

**Выбран баг №3 — исчезающая заметка.** Исходный коммит уже существует, новый коммит для старой версии не нужен. Можно открыть старую версию отдельно, не трогая текущие файлы:

```sh
mkdir -p /tmp/remotion-demo-before
git archive 17540b38b82f01e2584bdcfcd93d89dfb52567f5 | tar -x -C /tmp/remotion-demo-before
python3 -m http.server 8084 --directory /tmp/remotion-demo-before
```

1. Открыть `http://localhost:8084/#evidence` в отдельном профиле/приватном окне.
2. Открыть E02 (Robot diagnostic log), написать `Проверить время` и не нажимать Save note.
3. Выбрать Reviewed. До исправления текст исчезает: новое DOM-поле заполняется старым значением из хранилища.
4. Запустить текущую версию на другом порту: `python3 -m http.server 8085` из проекта. Повторить шаги — текст остаётся. Нажать Save note и перезагрузить: текст сохранён.
5. Показать изменение кода: `git diff 17540b3 -- modules/evidence_detail.js`.

**Ответ: какие действия и состояние вызывают ошибку?**
В поле уже есть новый текст, но в хранилище его ещё нет. Смена статуса перерисовывала карточку и подставляла старую сохранённую заметку. Теперь смена статуса не пересоздаёт поле ввода.

**Ответ: влияли ли исправления друг на друга?**
Да. После исправления кеширования Dashboard стали сразу видны изменения закладок и статуса. Но неверный выбор «недавних» улик остался отдельной причиной: для него понадобилась сортировка по дате. Ожидание всей загрузки также убрало раннюю отрисовку пустых разделов и сброс полей поздними ответами. А обработка текста заметки через `textContent` сама по себе не спасала несохранённый текст от перерисовки — это отдельное исправление. Поэтому проверялись конкретные сценарии каждого бага и затем весь интерфейс повторно.
