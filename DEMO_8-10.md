## Demo 8 — Clean coding: globals, `var`/`let`/`const`, code smells

### 1) Top-level globals in the original `app.js` and why they were dangerous

В текущем проекте в корневом [app.js](app.js) уже нет top-level `var` — это как раз один из результатов рефакторинга Demo 1: логику вынесли в ES modules, и корневой файл стал тонким bootstrap-слоем, а не местом для общего состояния.

Но если бы старый, «плоский» вариант всё ещё держал глобальные переменные, типичные проблемы были бы такими:

1. `latestSearchRequestId`  
   - Если две разные части кода начали бы писать в одну и ту же глобальную переменную, они бы мешали друг другу. Например: один поиск обновляет `latestSearchRequestId`, а другой — ещё раз, и старый ответ случайно «побеждает» в конце.
   - Уже исправлено: в модуле [modules/evidence_list.js](modules/evidence_list.js) это состояние живёт в области модуля, а не в глобальном объекте `window`.

2. `savedMessageTimer`  
   - Если два разных UI-элемента или два разных вызова `saveHypothesis()` использовали бы один и тот же глобальный таймер, один таймер мог бы сбросить другой. Результат — странные задержки и «мигающие» сообщения.
   - В модуле [modules/workspace.js](modules/workspace.js) таймер хранится как локальная переменная модуля и не конфликтует с остальным кодом.

3. `sortValue` / `results` / `html` в старом flat-коде  
   - Если разные функции используют одно и то же имя, можно случайно перезаписать чужие данные. Например, один кусок кода меняет `html`, а другой в этот же момент подставляет в него другой контент, и отладка превращается в «чья переменная выиграла».
   - В модулях логика разнесена по функциям и файлам, поэтому один модуль не видит локальные данные другого, если это не передано явно.

Итог: в этом проекте глобалы уже не живут в корне [app.js](app.js); это и есть правильная модель для ES modules.

### 2) Замена `var` на `const`/`let`

Проверка по проекту показала: `grep` по шаблону `\bvar\b` по всем JS-файлам ничего не нашёл. То есть все старые `var` уже заменены.

Принцип выбора был такой:

- `const` — если значение не меняется после инициализации;
- `let` — если оно позже перезаписывается.

Примеры из проекта:

- `const typeSelect = document.getElementById("filterType");` — значение не меняется.
- `let hash = window.location.hash.replace("#", "");` — значение может быть переопределено при выборе другого view.
- `let latestSearchRequestId = 0;` — счётчик должен расти.

`var` был опасен тем, что:

- он функционно-скопирован, а не блочно-скопирован;
- одна и та же переменная может «просачиваться» за пределы цикла или блока;
- в старом коде это создавалo баги, когда переменная из цикла использовалась позже, чем ожидалось.

### 3) Ещё два code smells и исправления

#### Code smell 1: повторная подписка на события при каждом рендере

В [modules/evidence_list.js](modules/evidence_list.js) раньше обработчик клика добавлялся заново при каждом вызове `renderEvidenceList()`. Это проблема, потому что:

- один и тот же элемент получает несколько одинаковых слушателей;
- один клик может обработаться дважды;
- отладка и ревью становятся сложнее.

Исправление:

- добавили флаг `container.dataset.clickBound` и подписываемся только один раз;
- теперь повторный рендер не создаёт дублей обработчиков.

#### Code smell 2: глубокая вложенная цепочка `.then()`

В [modules/data_loading.js](modules/data_loading.js) была последовательность загрузки `case.json -> people.json -> locations.json`, а затем `evidence.json` и `timeline.json`, вложенная через `.then()`. Это тяжело читать, потому что:

- каждая следующая загрузка начинается только после предыдущей;
- логика «что должно произойти дальше» рассыпана по нескольким уровням;
- ошибка в одном месте ломает весь поток и её трудно локализовать.

Исправление:

- перевели на `async`/`await`;
- оставили то же поведение: загрузка идёт строго по очереди, не параллельно;
- обработка ошибок сохранилась с `try/catch`.

## Demo 9 — Refactor nested Promises to `async`/`await`

### 1) Самая глубокая цепочка `.then()`

Самая глубокая часть была в [modules/data_loading.js](modules/data_loading.js):

- сначала `fetch("data/case.json")`
- потом внутри `.then()` `fetch("data/people.json")`
- потом внутри следующего `.then()` `fetch("data/locations.json")`
- после этого ещё шла загрузка evidence и timeline

То есть это была цепочка примерно 3–4 уровня глубины: один запрос должен успешно завершиться, чтобы стартовал следующий. Это было тяжело читать, потому что «внутри другого `.then()`» создаёт каскад логики.

### 2) Переписанный вариант с `async`/`await`

Теперь в коде используется такой порядок:

- `await fetch("data/case.json")`
- `await fetch("data/people.json")`
- `await fetch("data/locations.json")`
- затем `await loadEvidenceData()`
- затем `await loadTimelineData()`

Поведение сохранено: код всё ещё ждёт одну загрузку, чтобы начать следующую. Это важно: мы не перешли на параллельную загрузку, потому что в задаче это не было целью.

### 3) Ещё один `.then()`/`.catch()`/`.finally()` переписан под `async`/`await`

Сделано в [app.js](app.js):

- `initApp()` стал `async function initApp()`
- `await loadAllData()` и `await loadNoteAsync("E01")` заменили цепочку `.then()`
- поведение осталось тем же: сначала ждём загрузку данных, затем показываем хэш и выводим предупреждение/preview заметки

### 4) Проверка порядка выполнения

Порядок операций не изменился: в новой версии всё так же:

1. загрузить основной набор данных
2. отрисовать интерфейс после загрузки
3. получить первую заметку
4. только потом продолжить остальную логику

Это подтверждается тем, что мы явно сохранили последовательность `await`, а не поменяли её на параллельный запуск.

## Ответы на вопросы

### Вопрос 1: разница между `var`, `let`, `const`

- `var` — функциональная область видимости. Если объявить внутри блока, он всё равно может быть виден в функции.
- `let` — блочная область видимости. Видим только внутри `{ ... }`.
- `const` — тоже блочная область видимости, но нельзя переназначать.

Пример бага с `var`:

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
```

Результат: покажет `3` три раза, потому что `var` не создаёт новую переменную на каждой итерации. С `let` будет `0, 1, 2`.

Такой баг может появиться в UI-коде, когда несколько таймеров или обработчиков использовали один и тот же индекс цикла.

### Вопрос 2: accidental global

Accidental global — это переменная, созданная без объявления (`var`, `let`, `const`), но используемая в функции или в модуле.

Например:

```js
function bad() {
  counter = 1;
}
```

В старом нестрогом JavaScript это создаёт глобальный `counter` в `window`.

Теперь проект работает как ES modules, а модули в JavaScript всегда в strict mode. Поэтому если сделать ту же ошибку, браузер не создаст глобаль, а выбросит ошибку или остановит выполнение в строгом режиме.

### Вопрос 3: «технически работает» и «чисто» — не одно и то же

Хороший пример из этого проекта: глубокая цепочка `.then()` в [modules/data_loading.js](modules/data_loading.js). Она работала, но была тяжёлой для чтения и отладки.

Реальная цена грязного варианта:

- больше шанс допустить ошибку при изменении очередности загрузки;
- сложнее понять, почему данные не готовы в нужный момент;
- дольше разбираться новому разработчику;
- сложнее ревьюить и поддерживать.

После рефакторинга код стал проще читать, и логика проще проверяется пошагово.

### Вопрос 4: почему `async`/`await` читается проще

`.then()` — это «цепочка событий»: "сделай A, потом B, потом C". Внутри неё легко потерять контекст и запутаться в порядке. `await` читает по шагам:

```js
const data = await fetch(...);
const json = await data.json();
```

Это выглядит как обычный линейный код, хотя на самом деле всё ещё асинхронно.

### Вопрос 5: что делает `await`

`await` буквально говорит: "останови выполнение этой асинхронной функции и подожди, пока промис не завершится".

Пока функция ждёт, остальная программа не замирает — браузер продолжает обрабатывать события, клики, таймеры и остальной код. `await` приостанавливает только эту функцию, а не весь процесс.

### Вопрос 6: async-функция всегда возвращает Promise

Да. Даже если внутри есть `return 42`, результат будет Promise, который резолвится в `42`.

Пример:

```js
async function getValue() {
  return 42;
}

getValue().then(value => console.log(value));
```

Вывод будет: `42`.

То есть `.then()` вызывается не на числе, а на Promise, который вернулся из `async`-функции.

### Вопрос 7: эквивалент `.catch()`

Эквивалент `.catch()` — `try/catch` вокруг `await`:

```js
try {
  const result = await riskyCall();
} catch (error) {
  console.error(error);
}
```

Если забыть `try/catch`, промис, который отклоняется, просто всплывает как необработанная ошибка. В консоли это обычно выглядит как "Unhandled promise rejection" или аналогичная ошибка.

### Вопрос 8: быстрее ли `async`/`await` чем `.then()`

Не быстрее по сути. Это не оптимизация производительности. Это просто другой синтаксис для того же механизма промисов.

Что меняется:

- читаемость и поддерживаемость;
- порядок кода проще для разработчика.

Что не меняется:

- асинхронность и тайминги;
- факт, что операции всё ещё выполняются через очередь задач и Promise;
- последовательность выполнения, если мы не вводим параллельность специально.

### Вопрос 9: что будет, если убрать один `await`

Если убрать `await` в `async`-функции, то функция начнёт возвращать Promise сразу, не дожидаясь результата. Поэтому в коде появится ситуация, когда далее идёт работа с промисом как будто это уже готовые данные.

Это очень похоже на типичные баги из Demos 2–5: промис используется как если бы он уже был результатом вычисления. Суть одна и та же:

- не дождались завершения асинхронной операции;
- начали читать/использовать объект Promise вместо данных;
- логика ломается, потому что данные не готовы в нужный момент.

---

### Итого

- `var` — устаревшая и опасная модель;
- `let`/`const` лучше по области видимости и предсказуемости;
- ES modules и правильная разбивка на файлы уже уменьшили риски глобальных конфликтов;
- `async`/`await` делает код проще, но не делает его быстрее по сути.

Проверка: в проекте больше нет объявлений `var` в JS-файлах.

## Demo 10 — Refactor to arrow functions

### Что было сделано

Я выбрал безопасные места для перевода на стрелочные функции:

- в [modules/dashboard.js](modules/dashboard.js) функция `statCardHTML` стала стрелочной;
- в [modules/evidence_list.js](modules/evidence_list.js) функция `simulateAsyncSearch` стала стрелочной;
- в [modules/event_listener.js](modules/event_listener.js) обработчики `addEventListener` с `function (event)` и `function (e)` заменены на стрелочные функции.

Это хороший кандидат, потому что стрелочные функции здесь читаются проще и хорошо подходят для кратких колбэков, а `this` не нужен.

### Функция, которую я не стал переводить

Я бы не стал превращать `handleHashChange` из [modules/navigation.js](modules/navigation.js) в стрелку, потому что это публичная функция, которая используется как обычная callback/entry point, и логика вокруг нее проще и понятнее в стандартном объявлении. Для такого места не нужно выигрышное сокращение синтаксиса, а стрелка только добавила бы лишнюю путаницу.

### Ответы на вопросы

#### 1) Чем стрелки отличаются по `this`

У обычной функции `this` зависит от того, как её вызвали. У стрелки `this` берётся из внешнего лексического контекста.

Это делает стрелки рискованными как методы объекта:

```js
const obj = {
  value: 42,
  getValue: () => this.value
};
```

У стрелки `this` не будет `obj`, а будет внешний `this`. Поэтому для методов объекта обычно используют обычные функции.

Но для колбэков удобно: когда нужен `this` родительского контекста, а не DOM-элемента или объекта вызова, стрелка выигрывает.

#### 2) `new` и `arguments`

Стрелки нельзя вызывать через `new`, и у них нет своего `arguments`.

В этом проекте это не помешало перевести функции-helpers и колбэки, потому что они не использовали конструкторы и не зависели от `arguments`.

То что реально затронуло переводы: мы выбрали те функции, которые не требовали `this`, `arguments` или `new`.

#### 3) Hoisting

Обычная функция, объявленная через `function foo() {}`, поднимается наверх, поэтому её можно вызвать до объявления.

Стрелка, объявленная как `const foo = () => {}`, не hoistится так же. Это не стало проблемой, потому что мы рефакторили уже существующие функции и вызывали их только после их объявления в коде.

#### 4) Пример до/после

Было:

```js
function statCardHTML(value, label) {
  return '<div class="stat-card"><div class="stat-value">' + value + '</div><div class="stat-label">' + label + "</div></div>";
}
```

Стало:

```js
const statCardHTML = (value, label) => {
  return '<div class="stat-card"><div class="stat-value">' + value + '</div><div class="stat-label">' + label + "</div></div>";
};
```

Поведение на запуске почти то же самое: это просто другой синтаксис, без изменения логики. Разница чисто в стиле и читаемости.

#### 5) Нужное правило для команды

Хорошее правило: 

- обычные функции — для методов, экспортируемых функций и логики, где важна семантика вызова;
- стрелки — для коротких колбэков, `.map()`, `.filter()`, обработчиков событий, анонимных функций в UI.

Так код становится понятным: методы и публичные функции — привычно читаются, а короткие колбэки — компактны и не путают `this`.

---

### Коротко по сути

Стрелочные функции здесь были полезны там, где нужна короткая логика и не нужен `this`. Это улучшило читаемость без изменения поведения. Главное — не использовать стрелки там, где важен `this` или конструкторный вызов.
